# 안전한 저장과 서버 변경 이력 적용

## 적용 순서

1. 입력 작업을 잠시 중단하고 기존 운영 데이터와 스키마를 백업합니다. 마이그레이션과 앱 교체 사이에 구버전 서버가 저장하지 않도록 점검 시간을 확보합니다.
2. 기존 마이그레이션 적용 후 `supabase/migrations/20260923_workspace_integrity.sql`을 Supabase SQL 관리자 권한으로 실행합니다.
3. SQL 실행이 완료된 뒤 이 애플리케이션 버전을 배포합니다. 사용자에게 열린 탭을 닫고 다시 로그인하도록 안내합니다.
4. 서로 다른 관리자/입력자 세션으로 아래 검증을 수행합니다.

마이그레이션을 먼저 적용하지 않으면 API는 데이터베이스 업데이트 안내와 함께 저장을 거부합니다. 예전 방식으로 조용히 덮어쓰는 대체 경로는 없습니다. 기존 구버전 탭은 새 API에 필요한 revision 정보가 없으므로 새로 불러와야 합니다.

## 바뀌는 저장 계약

- `GET /api/workspace`: 사용자 범위의 `payload`와 scope별 `revisions`를 반환합니다. 존재하지 않는 법인 workspace의 revision은 0입니다.
- `PATCH /api/workspace`: `{payload, revisions, mutationId}`를 받습니다. 최신 revision과 다르면 HTTP 409로 전체 저장을 거절합니다.
- 데이터베이스 함수 `save_workspace_checked`가 비교·여러 scope 저장·행별 변경 이력을 한 트랜잭션에서 처리합니다. 하나라도 실패하면 전부 취소됩니다.
- 같은 요청 ID를 다시 보내면 원래 저장 결과를 반환합니다. 통신 오류로 응답을 받지 못한 경우 중복 변경 이력이 생기지 않습니다.
- 브라우저가 `workspace_states`를 직접 수정하는 권한은 회수됩니다. 기존 사용자 역할과 조회 범위는 유지하고, 서버 API가 편집 권한·사업장·상태를 검사합니다.
- 현재 JSON workspace 구조에서는 관리자와 입력자가 서로 다른 자료를 수정해도 공유 scope revision이 바뀌면 충돌할 수 있습니다. 이때 자동 병합하지 않으며, 최신 자료 확인 후 필요한 변경을 다시 적용합니다.

## 사용자 화면

- 서버의 저장 확인이 있어야 ‘서버 저장 완료’로 표시합니다. 전송 중 추가한 변경은 다음 요청으로 보냅니다.
- 통신 실패 시 다시 저장할 수 있습니다. 저장되지 않은 변경사항은 사용자별로 현재 탭의 sessionStorage에 임시 보존하고, 새로고침 후 복구 안내를 표시합니다. 저장 공간 제한·탭 종료까지 영구 보존을 보장하는 백업은 아니므로 내려받기 기능을 함께 제공합니다.
- 충돌 발생 시 편집을 일시 중단하고 내 변경사항 JSON 내려받기와 최신 자료 불러오기를 제공합니다. 최신 자료로 교체하기 전에 미저장 변경 폐기 여부를 확인합니다.
- 다른 탭이 공유 localStorage를 변경하면 현재 탭의 메모리 변경사항을 보존한 채 충돌 안내를 표시합니다.
- 서버 저장이 확인되지 않은 변경이 있을 때 페이지 이탈과 로그아웃을 확인합니다.

## 변경 이력 범위

- `workspace_change_log`는 저장된 배열 항목의 생성·수정·삭제와 설정 변경의 전후값, 로그인 사용자, DB 시각, revision을 보존합니다.
- 서버 이력 조회는 관리자 전용 `GET /api/workspace?view=audit&before=<id>`이며 100건씩 페이지를 넘깁니다. 응답은 `{entries,nextCursor}`입니다.
- 기존 클라이언트 audit 500건 목록은 과거 화면용 기록입니다. 서버의 새로운 이력은 이 제한을 사용하지 않습니다. 적용 이전의 잘린 이력은 복원되지 않습니다.
- `organizations`는 별도 조직 테이블에서 조회한 파생 목록이며 workspace 저장에서는 비워두므로 이력 대상에서 제외합니다. 별도 조직·사용자 관리 API 변경은 이 workspace 이력 범위 밖입니다.
- `audit` 캐시는 클라이언트가 보내는 서술이므로 서버 변경 이력의 원본으로 사용하지 않습니다.
- 변경 이력과 저장 영수증은 자동 삭제하지 않습니다. 추후 보존·아카이빙 정책을 정할 때 규정과 용량을 함께 검토해야 합니다.

## 검증

- `node --import tsx --test tests/workspace-integrity.test.ts`: revision 누락/충돌, 작성·제출·회수, 승인 권한, 확정자료 불변성, 법인·사업장 변경 차단.
- `scripts/verify-workspace-migration.mjs`: 별도 임시 설치한 `@electric-sql/pglite`의 `dist/index.js` 절대 경로를 `PGLITE_MODULE`에 지정하고 실행합니다. 운영 DB에 접속하지 않습니다. 실제 PostgreSQL에서 반복 migration, 복수 행 변경 이력, 동일 revision 동시저장, 재시도 중복 방지, 중간 오류 전체 rollback, append-only, 직접 쓰기 권한 차단을 검증합니다.
- 운영 적용 후: A/B 세션이 같은 revision을 읽고 A 저장→B 저장 시 B가 충돌하는지, B의 로컬 변경 내려받기가 가능한지, 관리자 이력에서 A의 변경 전후값과 사용자를 확인합니다.

## 마감과 재개

- 수집기간·정량 요청을 `마감` 또는 `잠금`으로 전환할 때 대상 사업장·기간별 입력 누락, 미승인, 미입력/부적절한 숫자, 비율의 분자·분모 오류를 서버와 화면에서 검사합니다. 실제 0은 유효한 값이고 해당 없음은 사유가 있어야 합니다.
- 기존 법인 단위 요청도 등록된 사업장 전체로 확인합니다. 사업장 정보가 없는 과거 자료는 여러 사업장을 동시에 충족한 것으로 간주하지 않습니다. 등록 사업장 자체가 없는 법인에 한해서 법인 단위 확인을 유지합니다.
- 이미 닫힌 요청이 포함된 다른 저장을 반복 검증하지 않습니다. 닫힌 요청의 자료를 바꾸려면 먼저 요청을 다시 열고 그 변경이 서버에 저장된 후 자료를 수정합니다. 재개와 자료 수정을 한 요청에 합쳐 보내면 거부합니다.
- 마감 전후 상태는 별도 클라이언트 스냅샷 대신 서버 변경 이력의 revision과 전후값으로 추적합니다.
- 추가 회귀 테스트: `tests/workspace-emissions.test.ts`, `tests/workspace-metrics.test.ts`, `tests/workspace-closing.test.ts`.
